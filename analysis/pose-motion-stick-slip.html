Go to pose 为什么仍然一顿一顿

上位机发出的目标轨迹是平滑的，卡顿发生在舵机里。流式下发每 20 ms 给一个只领先 2–3 步的位置目标，SCS0009 因此整个运动过程都处在“临近目标定位”的工况：只有比例控制、有 ±1 步死区，再遇上静摩擦，就形成“停住、憋力、突跳”的循环。速度寄存器用哪种模式不是原因。

上一份分析（pose-motion-jitter）把抖动归因于速度寄存器：舵机冲到目标后停下，等下一个目标。后来实施的对策包括 fixed 1000、按速度动态设置的 dynamic 模式、规划时长考虑加速度、速度前馈，以及轨迹记录。现在有了 19:06–19:34 的真机轨迹，可以直接检验这些对策：两种速度模式下，关节的停顿比例几乎一样，均为 20–36 % 的运动周期完全不动；目标轨迹本身也没有问题。真正的差别出现在单次写入的对照里：同一个关节、同样的速度，舵机自己生成轨迹时是连续运动的。

所以问题出在上位机怎样把轨迹交给舵机：每次只给一点点前方的目标，舵机的位置环会一次次在目标附近停下。

二、关节的实际运动：停住 → 憋力 → 突跳

逐周期看 ID 1：当误差（舵机当时持有的目标减去位置）为 1–3 步时，负载读数是 0，舵机根本不出力；误差积累到 4–7 步，负载升到 8–14 %，关节突破静摩擦后一个周期跳 4–6 步追上目标；落回 ±1 步以内，输出又归零，关节停下。每 5–8 个周期重复一次，即 6–10 Hz 的顿挫，这就是肉眼看到的卡顿。

突破静摩擦所需误差 ≈ 死区 + 静摩擦所需负载 ÷ （每步误差对应的负载）
ID 1：1 + 10 % ÷ ~2 %/步（P = 20）≈ 5–6 步，与实测的跳变幅度一致。

SCS0009 的位置环只有比例项：输出 ≈ P × 误差，P = 15 时约 1.5–1.7 % 负载/步。寄存器 26/27 的死区是 ±1 步，误差在 ±1 步以内时完全不出力。静摩擦大于动摩擦，所以关节一旦起步就会冲过平衡点、追上目标，然后停住。各关节的数据如下（fixed，grab）：

为什么会这样（推断）

单次写入时，舵机内部按速度寄存器生成的参考位置一路领先于关节，误差始终保持在死区之外，电机持续出力，关节一直处在动摩擦区。流式下发时，目标只比关节领先 2–3 步：

  • fixed（寄存器 1000）：内部参考约 6 ms 就走到这一周期的目标并停下。
  • dynamic（1.3 × v）：参考同样在周期结束前约 23 % 的时间就到达目标。

无论哪种模式，关节追近后误差都会落进死区，于是停下、被静摩擦“粘住”。换句话说，流式下发让舵机在整个运动中都处于“收尾定位”工况，而这个工况恰恰是它最差的。SCS0009 固件内部怎样生成速度轨迹没有公开文档，所以这一条是根据数据做的推断；下文 A0 的零代码试验可以直接验证。

四、加重卡顿的其他因素

速度设得低

8 个关节的 max_speed 现在都是 150，而速度扫描给出的建议值是 ID 1 266、ID 2 287、ID 6 282、ID 8 190。150 步/s 相当于每周期 3 步，和突破静摩擦所需的误差（4–6 步）是同一个量级。最小 jerk 曲线的起步和收尾段速度更低，每周期不到 1 步，停—跳最明显。摩擦在低速下最难处理（Stribeck 效应）。

P 增益偏低且不一致

ID 1、2 是 20，ID 6 是出厂值 15，其余是 45–50。停—跳的幅度大约和 P 成反比，滞后也是。各关节滞后不同，同一条最小 jerk 曲线在实际运动中就不再同步。

力受限关节

ID 3、4、5、7、8 需要 15–50 % 负载才能动。单次写入的轨迹里，ID 7、8 在收尾段有 3–4 s 的爬行（82–88 % 的周期不动），ID 2 停在离目标 4 步的地方。这类关节无论用哪种控制方式都会受摩擦和预紧影响。另外，ID 5 当前的 min-start 是 1，之前的调试记录显示 ≥ 1 会引起振荡，建议核对。

次要因素

目标取整到 1 步（约 0.29°）、50 Hz 更新、±3 ms 周期抖动：这三项都比 4–6 步的停—跳小一个量级。改成 100 Hz 也帮不上忙，因为每次更新后舵机参考仍会走到目标并停下。

五、改进方向

A. 带前瞻的流式下发（主要对策）

每周期发送的目标改为 setpoint(t + Tlead)，Tlead 约 0.1–0.2 s；速度寄存器 ≈ 当前轨迹速度 |v(t)|，增益约 1.0。这样舵机的内部参考就按轨迹速度连续前进，追不上目标，也不会停下，舵机一直处在单次写入那种工况。前瞻量从 0 开始随速度平滑增长，每包目标的变化仍是 2–4 步，不违反单包跳变上限。跟踪误差检查要改为对照不带前瞻的 setpoint(t)。

核心修复 · 改 worker 发送逻辑 · 先在 ID 1 上验证

A0. 零代码验证试验（先做）

只使能 ID 1，dynamic 模式，把 MotionConfig.stream_speed_gain 从 1.3 临时改成 0.8，跑同一个 grab。速度寄存器低于轨迹速度时，内部参考在一个周期内到不了目标，就会连续前进。如果停顿周期从约 30 % 明显下降，就证实了上面的机理。代价是滞后会累积，收尾段有一段慢速爬行，所以只用来做试验。

B. 提高 P 增益（并行）

ID 1、2 从 20 提到 30–35，ID 6 从 15 提到 25–30，每次提高不超过 10，并观察是否出现蜂鸣或振荡。突破所需误差和跳变幅度大约按 P 的比例缩小，ID 6 的滞后也会同步减小。

tune-servo · 原值已备份

C. 恢复实测的 max_speed

自由关节（ID 1、2、6、8）改回速度扫描的建议值，缩短低速段所占比例。力受限关节保持 150，直到机械问题解决。

config.py · 无风险

D. 机械：降低摩擦和预紧

食指（ID 3、4、5）和拇指（ID 7、8）的腱绳走线和预紧是摩擦的来源，也是力受限的根本原因。软件只能减轻它们的表现，不能消除。

硬件 · 与软件并行

不建议：上位机外环积分

在上位机侧加 PI，让目标随累计误差前移，看起来能补偿滞后。但积分器和静摩擦组合会产生自激的“猎振”（hunting），在 50 Hz 和 1 步分辨率下更难调，收益不如 A。

风险高

建议顺序

  1. A0：只使能 ID 1，stream_speed_gain = 0.8，对比停顿周期，用 5 分钟验证机理。
